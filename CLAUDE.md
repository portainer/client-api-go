# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A Go SDK for the **Portainer Business Edition** API. The module path is `github.com/portainer/client-api-go/v2`. SDK tags track the upstream Portainer server version (e.g. `v2.31.2` of the SDK targets Portainer 2.31.2).

Despite the neutral module name, the swagger source is the EE (`portainer-ee`) spec — generated model names carry the `Portaineree*` prefix.

**The Portainer API has no versioning contract.** Endpoints are not prefixed with a version (`/api/...`, not `/api/v1/...`) and there is no documented compatibility policy across Portainer server releases. Request/response shapes, field names, and even endpoint paths can change between server versions with no deprecation window. This is why:

- SDK tags are coupled 1:1 with server versions rather than following independent semver.
- Regenerating against a new server version is a routine, expected operation — not a rare event.
- Breaking changes can leak in from upstream without warning; diffing the regenerated `pkg/` after `make generate-client` is the only way to spot them.
- Pinning a specific SDK tag is the only reliable way for downstream consumers to target a specific server.

## Commands

```sh
# Regenerate the swagger client against a specific Portainer server version.
# Downloads swagger.yaml from SwaggerHub and runs go-swagger.
make generate-client VERSION=2.31.2

# Run tests (currently a no-op — there are none).
make test
# or
go test ./...
```

The Swagger CLI is pinned in `tools/go.mod` (a separate submodule, so its dependency graph does not leak into the SDK's runtime deps) and invoked by the Makefile via `go run -modfile=tools/go.mod ...`. No manual install or `$PATH` setup is required.

## Architecture

The repo has **two layered surfaces**, both publicly importable:

1. **`pkg/`** — swagger-generated client and models. Every file is marked `Code generated by go-swagger; DO NOT EDIT.` Do not hand-edit anything under `pkg/`; regenerate via `make generate-client` instead. `pkg/client/<resource>/` holds operation packages, `pkg/models/` holds DTOs (~470 files).

2. **`client/`** — hand-written "simple client" facade. `client.PortainerClient` wraps `pkg/client.PortainerClientAPI` and exposes ergonomic methods (`ListEndpoints`, `GetTeamByName`, `ProxyDockerRequest`, …). It is intentionally incomplete — README tells consumers to drop down to the swagger client for unsupported operations. New high-level methods belong here.

Inside `client/`:
- `client.go` — `NewPortainerClient(host, apiKey, opts...)` with functional `WithScheme` / `WithBasePath` / `WithSkipTLSVerify` options. Constructs **two** transports: a swagger `httptransport` for normal API calls and a separate `http.Client` (`ProxyClient`) for proxy passthroughs.
- `proxy.go` — Docker/Kubernetes proxy passthroughs, going through `ProxyClient` rather than the swagger transport.
- `utils/utils.go` — generic helpers like `BuildAccessPolicies[T]` translating role-name maps into Portainer access-policy DTOs. The role-name → role-ID mapping (`environment_administrator`=1, `standard_user`=3, …) is here.

`example/simple/` and `example/swagger/` show both usage modes.

## Working notes

- **Generated types currently leak through the `client/` facade** (e.g. `ListEndpoints` returns `[]*models.PortainereeEndpoint`). Be aware when designing new methods.
- **No `context.Context` is plumbed through any method** — preserve the existing signatures unless the change is intentionally breaking.
- **No tests, no CI** — verify changes manually against a running Portainer instance, or add `httptest`-based tests when modifying `client/`.
- **`AUDIT.local.md`** at the repo root tracks known issues and the plan for fixing them (the `.local` suffix keeps it out of public view; treat it as an internal working doc). Check it before starting work and tick items off as they are addressed.
- **Update `CHANGELOG.md` as you go.** When a change is user-visible (new method, behaviour change, bug fix, breaking change, dependency bump that affects consumers), add a one-line bullet under the matching category in `## [Unreleased]` as part of the same commit. Do not write a category section if it has no entries — leave it for `/release` to clean up. Internal-only changes (tests, refactors with no external effect, doc-only edits) do not need an entry.
- **Cutting a release** is done via the `/release` skill (`.claude/skills/release/`). Do not edit `Makefile`'s `VERSION`, `README.md` install examples, or rotate `[Unreleased]` by hand — let the skill do it so all the bumps stay in sync.
- `swagger.yaml` is checked in; treat it as a regeneration input, not as documentation to edit.
